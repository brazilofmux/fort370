fort370 for MVS 3.8j -- installing the compiler
===============================================

The MVS package is the compiler and its runtime:

  FORT370.xmit   one load module, FORT370: the FORTRAN 77 compiler,
                 which runs on the guest and writes S/370 assembler
  F77RT.xmit     the fort370 runtime as a library, the PDS F77RT, from
                 which the linkage editor or the loader takes, by
                 automatic call, what a compiled program uses of
                 fort370's runtime and of libc370; RECEIVEd as
                 FORT370.xmit is
  F77RT.upd      the same library as IEBUPDTE input, for a system
                 without RECEIVE; either one will do

Nothing here needs a C compiler on MVS.  Both were cross-built on a
host with mvslovers' cc370 and libc370, and these are the results.

These instructions do not go stale, but the figures below describe one
particular build.  Check them against whatever you actually downloaded
rather than against this file.

                596960 bytes, FB80 when it lands on the guest
  F77RT.xmit    SHA256 e509f2aef5386ec34eda7c3d02f0d3799db2e87fd8badff340b6beb08b4d9d82
                615440 bytes, FB80

1.  Get the two files onto the guest
------------------------------------

Each must arrive as a physical-sequential FB/80 data set, unchanged.
Both are binary: do not let anything translate them to EBCDIC or strip
trailing blanks.  Any route works -- FTP in binary with a pre-allocated
target, IND$FILE, or an emulated tape.  For tape, wrap the file in AWS
blocks and IEBGENER it in, as for any XMIT.

    //GEN      EXEC PGM=IEBGENER
    //SYSUT1   DD UNIT=480,VOL=SER=FORT01,LABEL=(1,NL),DISP=(OLD,KEEP),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSUT2   DD DSN=your.FORT370.XMIT,DISP=(NEW,CATLG),UNIT=SYSDA,
    //            SPACE=(CYL,(10,5)),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSPRINT DD SYSOUT=*
    //SYSIN    DD DUMMY

F77RT.xmit lands the same way, as your.FORT370.F77RT.XMIT (or F77RT.upd
as your.FORT370.F77RT.UPD); section 2 makes the runtime library of it.


2.  RECEIVE the compiler and the runtime library
------------------------------------------------

On TK5 the NJE38 RECEIVE is the one that works; it takes the whole
command on one line.

    //RECV     EXEC PGM=IKJEFT01,DYNAMNBR=60
    //SYSTSPRT DD SYSOUT=*
    //SYSPRINT DD SYSOUT=*
    //SYSTSIN  DD *
    RECEIVE INDATASET('your.FORT370.XMIT') -
      DATASET('your.FORT370.LOAD') DIR(5) NOPROMPT
    RECEIVE INDATASET('your.FORT370.F77RT.XMIT') -
      DATASET('your.FORT370.F77RT') NOPROMPT
    /*

  The library is a PDS of object decks, RECFM=FB, LRECL=80: each member
  one deck, named for an entry point it defines, with an alias for each
  of the others.  RECEIVE allocates it from the transmission.

Or, without RECEIVE, IEBUPDTE makes the same library of F77RT.upd:

    //LIB      EXEC PGM=IEBUPDTE,PARM=NEW
    //SYSPRINT DD SYSOUT=*
    //SYSUT2   DD DSN=your.FORT370.F77RT,DISP=(NEW,CATLG),UNIT=SYSDA,
    //            SPACE=(CYL,(2,1,40)),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSIN    DD DSN=your.FORT370.F77RT.UPD,DISP=SHR

  Each member is one object deck, named for an entry point it defines,
  with an alias for each of the others.  IEBUPDTE says IEB817I, "STOWED
  WITH TTR", for every member and alias: that is how it records a new
  one, and the step ends with return code 0.


3.  Run it
----------

    //FORT     EXEC PGM=FORT370,REGION=8192K
    //STEPLIB  DD DSN=your.FORT370.LOAD,DISP=SHR
    //SYSPRINT DD SYSOUT=*
    //SYSTERM  DD SYSOUT=*
    //SYSIN    DD DSN=your.SOURCE.PDS(PROGRAM),DISP=SHR
    //SYSPUNCH DD DSN=&&ASM,DISP=(NEW,PASS),UNIT=SYSDA,
    //            SPACE=(CYL,(2,2)),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSUT1   DD UNIT=SYSDA,SPACE=(CYL,(5,5))

  REGION=8192K is the recommendation.  The compiler's tables are about
  2.5MB, its two phases sharing most of them, and each phase takes up to
  1MB more while it runs; a small program compiles in about 4300K, and
  the largest units tested (FCVS FM912) need 6144K.  (The 2026-10-12
  package needs the full 8192K, those of 2026-10-13 to 2026-10-16
  7168K.)

  SYSIN is the source: fixed-form FORTRAN 77, any number of program
  units, columns 1-72 (73-80 are ignored).  It may be a data set or
  DD * -- the compiler reads it as libc370's standard input.

  SYSLIB, a PDS, is needed only by a source with INCLUDE: INCLUDE
  'name' reads its member NAME (see the language, below).  F77CLG has
  none; add //FORT.SYSLIB DD DSN=your.INCLUDE.PDS,DISP=SHR after the
  EXEC F77CLG.

  SYSUT1 is a work data set.  The compiler reads the source twice,
  once to find its program units and once to compile each, holding
  one unit at a time rather than the file; SYSIN can be read only
  once, so the first reading copies it to SYSUT1.  Without SYSUT1 the
  whole source is kept in storage instead, which limits it to a few
  hundred kilobytes beside the compiler's tables.  (The 2026-10-12
  package predates this: it keeps the source whole, up to 256K, and
  has no use for SYSUT1.)

  SYSPUNCH receives the S/370 assembler, one CSECT per program unit
  and one per COMMON block.  Feed it to IFOX00 with PARM='OBJ,NODECK'
  -- without OBJ it assembles cleanly and produces nothing.

  Errors go to SYSTERM with the line number and the statement (in an
  included text, the member's name and its own line).  The step's
  return code is the worst severity reported, as IBM's compilers give
  it: 0 a clean compile; 4 warnings only (a source that ends without
  an END statement, which FORTRAN H stops at with 16), and the
  assembler is complete; 8 errors, and SYSPUNCH is then incomplete;
  12 a unit too large for one of the compiler's tables; 16 no compile
  at all (no storage, the source or SYSPUNCH not to be had).  F77CLG
  goes on after a 4 and stops at an 8, COND=(4,LT,FORT), as FORTHCLG
  does.  (Through release 2026-10-24.1, every error ended with 1.)

  The listing goes to SYSPRINT, as FORTRAN H's does, and looks like
  H's: each program unit begins a page, with the options in effect;
  then its source, each statement numbered as H numbers it (ISN 2 is
  the first; comments and continuation lines are not numbered); its
  messages, each citing its statement's ISN and its severity; and its
  statistics.  The step ends with its own.  Give SYSPRINT a DCB of
  RECFM=FBA,LRECL=133 (F77CLG's does): without it the carriage control
  prints as text.  Without a SYSPRINT DD there is no listing, and the
  messages are still on SYSTERM.

  The options are FORTRAN H's, in PARM, and so are their defaults:
  NAME=MAIN, OPT=00, LINECNT=50, SIZE=0000K, SOURCE, EBCDIC, NOLIST,
  NODECK, LOAD, NOMAP, NOEDIT, NOID, NOXREF.  NOSOURCE leaves the
  source out of the listing (not the messages), and LINECNT sets the
  lines on a page; the rest are taken and shown in the listing, but do
  nothing yet.  An option H does not have is a warning.  With F77CLG,
  //RUN EXEC F77CLG,PARM.FORT='NOSOURCE'.  (A PARM of two data set
  names, dd:SRC dd:ASM, still names the source and the output.)


4.  Link and run a program
--------------------------

F77RT is the link's SYSLIB, and the linkage editor's automatic call
takes from it what the program calls of fort370's runtime and of
libc370, and nothing else.  The program's own object names the rest: a
compiled main program carries the entry point F77@GO, which goes on to
libc370's startup, @@CRT0, which calls the Fortran main program (CSECT
F77MAIN).  So the link needs no ENTRY statement and no INCLUDE:

    //LKED     EXEC PGM=IEWL,PARM='MAP,LET,LIST',REGION=2048K
    //SYSLIN   DD DSN=&&OBJ,DISP=(OLD,DELETE)
    //SYSLIB   DD DSN=your.FORT370.F77RT,DISP=SHR
    //SYSLMOD  DD DSN=&&LOAD(GO),DISP=(NEW,PASS),UNIT=SYSDA,
    //            SPACE=(TRK,(30,10,5))
    //SYSUT1   DD UNIT=SYSDA,SPACE=(CYL,(5,5))
    //SYSPRINT DD SYSOUT=*

  Every byte of F77RT's sections is text, zeros included.  IEWL fills
  storage no text record covers from its own buffers, and C assumes
  its static storage starts as zeros; without the zeros a program
  abends in libc370's stdio at its first WRITE.  A program's own
  storage follows FORTRAN's rule instead: undefined until assigned or
  given by DATA, as with IBM's compilers.

  NCAL would turn automatic call off and leave the runtime out.  A
  program that prints takes about 130K of the runtime, one that also
  computes a SQRT about 150K, and LINPACK about 220K.

The loader (PGM=LOADER, IEWLDRGO) takes the same SYSLIN and runs the
program without a load module, but it builds the whole program in the
storage its SIZE option gives it, whatever the REGION: the default is
too small for the runtime and a program of any size, which ends with
IEW1194 AVAILABLE STORAGE EXCEEDED.  Give it SIZE, the program's size
and room (a program with a 1MB array loads in SIZE=3072K), and a
REGION with the runtime's 230K more:

    //GO       EXEC PGM=LOADER,PARM='SIZE=1024K',REGION=4096K
    //SYSLIN   DD DSN=&&OBJ,DISP=(OLD,DELETE)
    //SYSLIB   DD DSN=your.FORT370.F77RT,DISP=SHR
    //SYSLOUT  DD SYSOUT=*
    //FT06F001 DD SYSOUT=*,DCB=(RECFM=FBA,LRECL=133,BLKSIZE=133)

  It takes its entry point, F77@GO, from the program's object, as
  IEWL does; leave EP= out.

F77CLG.jcl beside this file is a cataloged procedure that chains the
whole thing: FORT370 -> IFOX00 -> IEWL -> GO, in one job.  As in IBM's
FORTHCLG, its GO step's FT05F001 is DDNAME=SYSIN, so a program's input
for unit 5 is a //GO.SYSIN DD * after the EXEC; without one, unit 5 is
at its end at once.

  One job may run F77CLG once for each of several programs.  Each step
  tests only the return codes of its own invocation (COND=(4,LT,FORT)),
  and the assembler text and object are unnamed temporary data sets,
  reached by referback, so a program that fails to compile or ends
  with a nonzero code stops only itself.  A procedure of your own that
  is run several times in one job wants the same: COND=(0,NE) with no
  step name tests every step before it in the job, and a temporary
  name such as &&ASM is the job's, not the step's, so a later step's
  DISP=OLD finds the first one still passed, an earlier program's.

  The assembly step's SYSPRINT is DUMMY: what FORT370 writes assembles
  cleanly, and a listing of it is thousands of lines.  If the ASM step
  ends with return code 8 anyway, it is a compiler bug -- please report
  it -- and IFOX00's messages say where.  To see them, add

    //ASM.SYSPRINT DD SYSOUT=*

  after the EXEC F77CLG statement.  (PARM='NOLIST' is no shortcut:
  IFOX00 then leaves out its error messages with the listing.)

  Give the program's step a REGION.  Its arrays and COMMON are static
  storage in the module, beside the runtime it uses, and the runtime
  takes about 70K more when it starts, mostly its C stack: a program
  with no arrays that prints runs in 208K.  SYSPRINT, SYSTERM and SYSIN are opened
  only if the program uses them (a unit 5 or 6 without its DD, unit 0,
  a message), each with a buffer of the DD's block size, 32K when the
  DD gives none.  The default
  region of a job class can be too small for that, and the program
  then ends at once with return code 12 and no output.  F77CLG's GO
  step asks for 4096K, which the kernels in bench/kernels fit in with
  room.

When the program runs, a Fortran unit n, 0 to 99, is the DD FTnnF001:
unit 6 is FT06F001 (SYSPRINT when there is no FT06F001), unit 5
FT05F001 (SYSIN when there is none), unit 0 FT00F001 (SYSTERM when
there is none).  OPEN FILE='NAME' names a DD.  A subprogram's local
variables keep their values from one call to the next, as FORTRAN H's
and VS FORTRAN's do, with or without SAVE.  A direct-access
file is a DASD data set of fixed blocks, RECL bytes each; a new one is
formatted as it is written.  A unit opened with STATUS='SCRATCH'
needs its DD as well; fort370 allocates none.  STOP ends the program
with its code as the step's return code.

A format in a CHARACTER variable, array or expression is checked when
the statement uses it, as the compiler checks a FORMAT statement, and
its blanks outside its strings and nH text are not significant:
( 3I 2) is (3I2).  A format certainly wrong, (HI,MOM) among them, ends
the program with a message naming it (a READ with ERR= or IOSTAT=
takes that instead), and so does a format with no data edit
descriptor when items are left to transfer.

A specific intrinsic named in INTRINSIC may be passed as an actual
argument (F77 15.9.3), the COMPLEX and COMPLEX*16 ones among them
(CSQRT, CDSQRT, CONJG, DCONJG, CDABS, DIMAG and the rest), and gives
through the dummy procedure what a direct call gives, to the bit.  As
in FORTRAN IV, EXTERNAL SQRT (or SIN, CSQRT...) with no subprogram of
that name in the source names the library's function: passed, it is
that function, and SQRT(X) calls it.  A SQRT of the program's own
must then be in the same source; one compiled separately is not the
one EXTERNAL SQRT reaches.

A subprogram may have any name but F77MAIN, F77@GO and the runtime's
own, which begin F77.  The names libc370 uses inside F77RT begin with
#, out of a program's way.  A subprogram named SQRT, SIN, EXP, EXIT
or another of the functions FORTRAN H's library also has replaces the
library's, as it does under FORTRAN H.

The language is FORTRAN 77 with IBM's COMPLEX*16 (DOUBLE COMPLEX
too): its constants, a complex constant with a DOUBLE PRECISION part,
(1.D0,2.D0); FORTRAN H's DCMPLX, DCONJG, CDABS, CDSQRT, CDEXP, CDLOG,
CDSIN and CDCOS, later IBM's DIMAG and DREAL, and the generic names
(ABS, SQRT, REAL, AIMAG, CONJG...) taking it as gfortran's do.  As in
H, COMPLEX with DOUBLE PRECISION is COMPLEX*16.  REAL*8 and COMPLEX*16
may be written in type statements, IMPLICIT, after a name (COMPLEX
Z*16) and before FUNCTION.  INTEGER*2 is a halfword and LOGICAL*1 a
byte, as in H: in arrays, COMMON, EQUIVALENCE, DATA and unformatted
records they take 2 bytes and 1, COMMON is not padded after them, and
a value stored in an INTEGER*2, by assignment or READ, keeps its low
16 bits, sign extended (40000 is -25536).  In an expression they are
fullwords, as H computes them.  A FUNCTION's length may follow its
name, INTEGER FUNCTION F*2(I) and CHARACTER FUNCTION C*8(X), or its
type.  Other lengths are accepted and get a fullword.
From MIL-STD-1753 (1978): END DO, as a labelled DO's terminal
statement, and DO WHILE (e), labelled or not.  And, as VAX FORTRAN and
later Fortran 90 have it, a DO without a label ended by END DO, and a
labelled DO WHILE ended by any statement bearing the label.  Also
from MIL-STD-1753, its bit functions, compiled in line: IAND, IOR,
IEOR, NOT, ISHFT, ISHFTC, IBITS, BTEST, IBSET, IBCLR and the
subroutine MVBITS, on fullword INTEGERs, bit 0 the rightmost; and its
constants in DATA, Z'1F' and O'17', and H's hexadecimal ones, Z1F,
right-justified in the item whatever its type (DATA X /Z41100000/ is
1.0), zeros on the left, the leftmost digits of a constant too long
for the item lost, as in H.  Among a DATA statement's values, ZFF is
that constant unless a PARAMETER has the name.  And MIL-STD-1753's
INCLUDE, written INCLUDE 'name', INCLUDE (name) or INCLUDE name alone
on its line, which copies the text it names into the source there: on
MVS the member NAME of the PDS on the compile step's SYSLIB, the
name's directory and extension dropped and its letters made capitals
(INCLUDE 'common.inc' is member COMMON), so a source and its texts
written on a host move to MVS unchanged; on a host the file, beside
the source or in the current directory, as written or in lower case,
with or without .f, .for or .inc.  An included text may include
another, but not one it is being read from.

Zw editing is H's, of any type but CHARACTER: output is the item's
bytes in hexadecimal, leading zeros kept, blanks on the left of a
field wider than the item and the rightmost digits in one narrower (Z4
of 1.0 is 0000); a COMPLEX item is two REAL ones.  Input takes blanks
as zeros wherever they are, right-justifies the digits in the item,
loses the leftmost of a field too wide, and a minus sign sets the
item's sign bit (-0000001 is 80000001).

NAMELIST is FORTRAN H's: NAMELIST /GROUP/ A, B, C, then READ (u,
GROUP) and WRITE (u, GROUP), or NML=GROUP.  WRITE writes H's records:
&GROUP, then NAME=value,... and &END, each record beginning with a
blank, the fields H's widths.  H fills 132 columns; here a record is
as long as the unit's DD says (LRECL, less 4 for RECFM=V; 133 when
nothing says), so a NAMELIST written to an FB/80 data set can be
punched, and H reads it back.  READ takes &GROUP or $GROUP up to &END,
$END or /: NAME=, NAME(i,j)=, r*value, values left empty, and H's own
records, a blank for the exponent's + among them; other groups' data
before it are skipped.  A CHARACTER item, which H has not, is written
and read as 'text'.  An item may be a dummy argument; an assumed-size
array's last dimension counts as 1.

DEFINE FILE is FORTRAN IV's direct access, as H does it: DEFINE FILE
a(m,r,f,v) gives unit a m records of r bytes (f E, formatted, or L,
either) or r words (U, unformatted), read and written as READ (a'n,
fmt) list and WRITE (a'n, fmt) list, without fmt when unformatted.
v, an INTEGER variable, is the number of the record after the last
one each statement reached, wherever in the program it is; FIND (a'n)
sets it to n and transfers nothing.  A DEFINE FILE has
effect in its whole unit (in a subprogram, from its first call), even
one a GO TO goes round.  The DD FTnnF001 is a DASD data set with room
for the m records; the first WRITE writes all of them, blanks, then
its own, as H's does.  As in H, a formatted record longer than r is
cut, with IHC212I and IHC231I; an input field past a record's end is
blanks, with IHC212I and the record; an unformatted list longer than
a record goes on into the next, the last filled with zeros; and a
record number outside 1 to m (IHC232I), or a READ before the data set
has been written (IHC236I), skips the statement, ERR= or no.  Each is
FORTLIB's message, its traceback and STANDARD FIXUP TAKEN, counted in
the summary of errors.  PUNCH f, list writes to unit 7, FT07F001, each
record as its format makes it, with no carriage control.

Floating point, measured against the exact values (2026-10-15, TK5;
a unit is one in the last hexadecimal place of the result):

  Constants and READ: a decimal number in the source and the same
  number read by E, F, D, G or list-directed input are the same value,
  the nearest one of the format.  FORTRAN H truncates a REAL one, so a
  REAL constant here can be one unit above H's (0.1 is 4119999A, H's
  41199999), and so can whatever a program computes from it; H's
  DOUBLE PRECISION ones are up to 8 units off either way.

  Output: E, F, D and G editing print the value's own digits, rounded
  at the last one printed, to any width; a half rounds away from zero.
  H's DOUBLE PRECISION output can be a few units off in the 16th digit
  and pads with zeros past the 17th.
  List-directed output prints 9 digits for REAL and 18 for DOUBLE
  PRECISION, correctly rounded, enough that READ gives back the same
  bits for every value (17, the IEEE count, leave a quarter of HFP's
  long values a unit off).  FORTRAN H has no list-directed I/O.

  Arithmetic is the machine's own, the same as H's to the bit.  So are
  SNGL, FLOAT, IFIX and the integer power X**I (repeated multiplication;
  X**39 can be 150 or 200 units off, in both).  A constant expression the
  compiler works out gives the bits the running program would.

  REAL functions are computed in long precision and cut to short:
  within a unit, and nearly always the exact value truncated, at any
  argument.  FORTLIB's short routines, which H's programs call, round
  SQRT and EXP and use their own approximations for the others, up to
  nine units off (SIN, ATAN2), and X**Y over 300.  The two agree bit
  for bit for some arguments only; a program that feeds such results
  back into itself (a network training, an integration) carries the
  difference along, and its printed REAL values can part from H's in
  the seventh significant digit: Xortran's loss after 20 epochs is
  0.197064698 here and 0.197064757 under H.  Where TANH is within a
  unit of 1, H returns 1.0.

  DOUBLE PRECISION functions: DSQRT is correctly rounded, as FORTLIB's
  is.  DEXP, DLOG, DLOG10, DATAN, DATAN2, DASIN, DACOS, DSINH, DCOSH,
  DTANH, DTAN and D**D are within 0.7 of a unit, and correctly rounded
  for all but about one argument in a hundred; FORTLIB's are within 1
  or 2 (DLOG10 6, DATAN2 5, D**D 400; DTAN off by thousands even at
  |x| < 20).  DSIN and DCOS are within 2 units for any argument;
  FORTLIB's are off by thousands at |x| < 20 as well.  FORTLIB's
  routines, hand-written assembler, take a fifth to a tenth of the
  time of these.

  COMPLEX functions (CSQRT, CEXP, CLOG, CSIN, CCOS, CABS) are within a
  unit of the result's magnitude; FORTLIB's, 14.  So is complex
  division, done in double precision, where FORTLIB's is within 12.

  COMPLEX*16 functions, at the 46 arguments of tests/s370/zmath.f that
  FORTLIB takes (2026-10-24, TK5), in units of the result's magnitude:
  CDABS 0.5 (FORTLIB 2.1), CDSQRT 0.7 (1.5), CDLOG 0.6 (2125, near the
  unit circle, where log|z| is small), CDEXP 1.7 (25), CDCOS 1.8
  (10,281) and CDSIN 2.2 (4.6 million).  Each is summed in extended
  precision and rounded once.  Arguments past FORTLIB's limits get its
  messages and fixups, as below.

  SIN, COS and TAN reduce an argument exactly, by the bits of 2/pi, up
  to FORTLIB's limits, pi*2**18 for REAL and pi*2**50 for DOUBLE
  PRECISION (past them, the error below); below that FORTLIB's DOUBLE
  PRECISION results have lost seven of their sixteen digits by 10**6.
  MOD, AMOD and DMOD, though, are the textbook a-INT(a/b)*b, and when
  a/b is past an integer's range the result means nothing, in both.

Errors are FORTLIB's.  An overflow in arithmetic (1.0E70*1.0E70), an
underflow and a division by zero are intercepted, IHC207I, IHC208I and
IHC209I, and the program carries on with the largest number after an
overflow, zero after an underflow and the dividend after a division
(1/0 is 1).  A function's argument out of its domain gets FORTLIB's
message and its standard fixup: SQRT(-4.0) is 2.0 with IHC251I,
ALOG(0.0) the largest negative number and ALOG(-1.0) 0.0, both with
IHC253I, ARSIN(1.5) 0.0, SIN(1.0E10) 0.7071068, TAN at a singularity
the largest number, (-2.0)**0.5 1.4142135 and 0.0**0.0 and 0**0 zero,
each with its message, as H's are -- run on TK5 side by side.  So do
the COMPLEX and COMPLEX*16 functions': CEXP((200.0,1.0)) is the
largest number times (COS(1.0),SIN(1.0)) with IHC271I, and CEXP of an
imaginary part past pi*2**18 zero with IHC272I; CLOG((0.0,0.0)) the
largest negative number with IHC273I; CSIN and CCOS of a real part past
pi*2**18 zero with IHC274I, and of an imaginary part past 174.673 half
the largest number times the sine or cosine of the real part, with
IHC275I; (0.0,0.0)**0 and **-1 zero with IHC246I; and the same for
COMPLEX*16, IHC281I-IHC285I and IHC247I.  The limits are FORTLIB's as
it tests them, a little off the ones its messages give: EXP's 174.673
is 174.6730957 (X'42AEAC50'), where the result would overflow, and
DEXP's 174.6730804; SINH's 175.366 is 175.3662262; SIN's and TAN's
pi*2**18 823549.625, but CSIN's and CEXP's 823296.0; DSIN's pi*2**50
3537118706008064.0.  Five
messages of each number are printed, each followed by a traceback, the
routines back to the main program with the registers each was called
with, and STANDARD FIXUP TAKEN; the tenth error of a number ends the program after IHC900I with
return code 16; and a program that had any ends with a SUMMARY OF
ERRORS.  The messages go to unit 6 with the program's own records.

Where it differs from FORTLIB: the traceback has no ISNs (H's has none
at OPT=2 either), and names the main program F77MAIN; a subprogram the
compiler put in line in its caller is not a routine of its own there.
ERRSET, which changes the counts, is not there.  An underflow inside
EXP (EXP(-200.0)) or ** is zero without a word, where FORTLIB's EXP
reports its own IHC208I.  A division whose quotient is never used is
not compiled at all, so it cannot be an error; H compiles it, and says
IHC209I.  A fixup that takes a sine or cosine, CEXP's and CSIN's, takes
this runtime's, a unit or two from FORTLIB's in COMPLEX and a few units
in COMPLEX*16.  CABS and CDABS of a value past the largest number are
the largest number without a word, where FORTLIB's CABS overflows and
says IHC207I.  An object compiled by an earlier fort370 calls the REAL
functions' names for DOUBLE PRECISION too (DSQRT was SQRT): its values
are the same, and an error in one is reported in the REAL function's
words.

IBM's names ARSIN, ARCOS, DARSIN and DARCOS are ASIN, ACOS, DASIN and
DACOS.


Rebuilding it yourself
----------------------

You need mvslovers' cc370 toolchain and libc370 installed -- cc370
1.6.3 with libc370 2.16.0, which cc370's install.sh puts in place
together (with maclib370) -- with that cc370 first on PATH, and then,
from a fort370 checkout:

    make mvs

which builds out/mvs/FORT370.xmit (the compiler, with cc370) and
out/mvs/F77RT.xmit and F77RT.upd (the runtime library, with the libc370
members the runtime calls, bench/mkrtlib.py, which also links every test
program from it the way automatic call does; bench/xmitpds.py writes the
TRANSMIT form, and reads it back to check it).  The assembler's and linker's clock is pinned
(MVSDATE, MVSTIME in the Makefile), since as370 and ld370 stamp the
date and time into what they write; two builds of the same source are
then the same bytes, and the SHA256 above reproduces.

  --sparse-text leaves the compiler's zeroed tables out of the module:
  program fetch hands over storage no text record covers as zeros.
  That is how MVS 3.8j behaves rather than something it promises; it
  is what cobc370 relies on too.

  -O1 because cc370's backend documents -O2 and above as unsafe on this
  target (the runtime was miscompiled at -O2: a double argument's store
  scheduled past the call).

bench/port-sweep.py is the proof that the compiler on MVS is the
compiler on the host: it compiles every FCVS program and every test on
the guest and diffs the assembler, byte for byte, with the host's.
