fort370 for MVS 3.8j -- installing the compiler
===============================================

Two files make the MVS package:

  FORT370.xmit   one load module, FORT370: the FORTRAN 77 compiler,
                 which runs on the guest and writes S/370 assembler
  F77RT.obj      the fort370 runtime as object decks, for IEWL to link
                 a compiled program with: fort370's runtime and the
                 libc370 members it calls, about 290K in a program

Nothing here needs a C compiler on MVS.  Both were cross-built on a
host with mvslovers' cc370 and libc370, and these are the results.

These instructions do not go stale, but the figures below describe one
particular build.  Check them against whatever you actually downloaded
rather than against this file.

                525680 bytes, FB80 when it lands on the guest
  F77RT.obj     SHA256 594bddcda2e8d8cf59b78e881f4e30bea4d4cdb28f18b895db47ebf5b180c987
                422160 bytes, FB80
  built         from fort370 356c477 (release 2026-10-16.1) with mvslovers/cc370 and libc370

1.  Get the two files onto the guest
------------------------------------

Each must arrive as a physical-sequential FB/80 data set, unchanged.
Both are binary: do not let anything translate them to EBCDIC or strip
trailing blanks.  Any route works -- FTP in binary with a pre-allocated
target, IND$FILE, or an emulated tape.  For tape, wrap the file in AWS
blocks and IEBGENER it in, as for any XMIT.

    //GEN      EXEC PGM=IEBGENER
    //SYSUT1   DD UNIT=480,VOL=SER=FORT01,LABEL=(1,NL),DISP=(OLD,KEEP),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSUT2   DD DSN=your.FORT370.XMIT,DISP=(NEW,CATLG),UNIT=SYSDA,
    //            SPACE=(CYL,(10,5)),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSPRINT DD SYSOUT=*
    //SYSIN    DD DUMMY

F77RT.obj lands the same way, as your.FORT370.F77RT, and is used as it
is: it is the runtime's object decks end to end, read by IEWL as part of
SYSLIN (section 4).


2.  RECEIVE the compiler into a load library
--------------------------------------------

On TK5 the NJE38 RECEIVE is the one that works; it takes the whole
command on one line.

    //RECV     EXEC PGM=IKJEFT01,DYNAMNBR=60
    //SYSTSPRT DD SYSOUT=*
    //SYSPRINT DD SYSOUT=*
    //SYSTSIN  DD *
    RECEIVE INDATASET('your.FORT370.XMIT') -
      DATASET('your.FORT370.LOAD') DIR(5) NOPROMPT
    /*


3.  Run it
----------

    //FORT     EXEC PGM=FORT370,REGION=8192K
    //STEPLIB  DD DSN=your.FORT370.LOAD,DISP=SHR
    //SYSPRINT DD SYSOUT=*
    //SYSTERM  DD SYSOUT=*
    //SYSIN    DD DSN=your.SOURCE.PDS(PROGRAM),DISP=SHR
    //SYSPUNCH DD DSN=&&ASM,DISP=(NEW,PASS),UNIT=SYSDA,
    //            SPACE=(CYL,(2,2)),
    //            DCB=(RECFM=FB,LRECL=80,BLKSIZE=3120)
    //SYSUT1   DD UNIT=SYSDA,SPACE=(CYL,(5,5))

  REGION=8192K is the recommendation.  The compiler's static tables are
  about 4MB, and each phase takes up to 1MB more while it runs; the
  largest units tested (FCVS FM912) need 7168K.  (The 2026-10-12 package
  needs the full 8192K, and the first package of 2026-10-13 6656K.)

  SYSIN is the source: fixed-form FORTRAN 77, any number of program
  units, columns 1-72 (73-80 are ignored).  It may be a data set or
  DD * -- the compiler reads it as libc370's standard input.

  SYSUT1 is a work data set.  The compiler reads the source twice,
  once to find its program units and once to compile each, holding
  one unit at a time rather than the file; SYSIN can be read only
  once, so the first reading copies it to SYSUT1.  Without SYSUT1 the
  whole source is kept in storage instead, which limits it to a few
  hundred kilobytes beside the compiler's tables.  (The 2026-10-12
  package predates this: it keeps the source whole, up to 256K, and
  has no use for SYSUT1.)

  SYSPUNCH receives the S/370 assembler, one CSECT per program unit
  and one per COMMON block.  Feed it to IFOX00 with PARM='OBJ,NODECK'
  -- without OBJ it assembles cleanly and produces nothing.

  Errors go to SYSTERM with the line number and the statement, and the
  step ends with return code 1; SYSPUNCH is then incomplete.


4.  Link and run a program
--------------------------

The program's object deck is linked with F77RT by concatenation: F77RT
ends in the control statement ENTRY @@CRT0, libc370's entry, which
calls the Fortran main program (CSECT F77MAIN).

    //LKED     EXEC PGM=IEWL,PARM='MAP,LET,LIST,NCAL',REGION=2048K
    //SYSLIN   DD DSN=&&OBJ,DISP=(OLD,DELETE)
    //         DD DSN=your.FORT370.F77RT,DISP=SHR
    //SYSLMOD  DD DSN=&&LOAD(GO),DISP=(NEW,PASS),UNIT=SYSDA,
    //            SPACE=(TRK,(30,10,5))
    //SYSUT1   DD UNIT=SYSDA,SPACE=(CYL,(5,5))
    //SYSPRINT DD SYSOUT=*

  Every byte of F77RT's sections is text, zeros included.  IEWL fills
  storage no text record covers from its own buffers, and C assumes
  its static storage starts as zeros; without the zeros a program
  abends in libc370's stdio at its first WRITE.  A program's own
  storage follows FORTRAN's rule instead: undefined until assigned or
  given by DATA, as with IBM's compilers.

F77CLG.jcl beside this file is a cataloged procedure that chains the
whole thing: FORT370 -> IFOX00 -> IEWL -> GO, in one job.

  The assembly step's SYSPRINT is DUMMY: what FORT370 writes assembles
  cleanly, and a listing of it is thousands of lines.  If the ASM step
  ends with return code 8 anyway, it is a compiler bug -- please report
  it -- and IFOX00's messages say where.  To see them, add

    //ASM.SYSPRINT DD SYSOUT=*

  after the EXEC F77CLG statement.  (PARM='NOLIST' is no shortcut:
  IFOX00 then leaves out its error messages with the listing.)

  Give the program's step a REGION.  Its arrays and COMMON are static
  storage in the module, beside about 175K of runtime, and the runtime
  takes about 230K more when it starts (its C stack and libc370's own
  storage): a program with no arrays runs in 412K.  The default
  region of a job class can be too small for that, and the program
  then ends at once with return code 12 and no output.  F77CLG's GO
  step asks for 4096K, which the kernels in bench/kernels fit in with
  room.

When the program runs, a Fortran unit n, 0 to 99, is the DD FTnnF001:
unit 6 is FT06F001 (SYSPRINT when there is no FT06F001), unit 5
FT05F001 (SYSIN when there is none), unit 0 FT00F001 (SYSTERM when
there is none).  OPEN FILE='NAME' names a DD.  A subprogram's local
variables keep their values from one call to the next, as FORTRAN H's
and VS FORTRAN's do, with or without SAVE.  A direct-access
file is a DASD data set of fixed blocks, RECL bytes each; a new one is
formatted as it is written.  STOP ends the program with its code as
the step's return code.

The language is FORTRAN 77 with IBM's COMPLEX*16 (DOUBLE COMPLEX
too): its constants, a complex constant with a DOUBLE PRECISION part,
(1.D0,2.D0); FORTRAN H's DCMPLX, DCONJG, CDABS, CDSQRT, CDEXP, CDLOG,
CDSIN and CDCOS, later IBM's DIMAG and DREAL, and the generic names
(ABS, SQRT, REAL, AIMAG, CONJG...) taking it as gfortran's do.  As in
H, COMPLEX with DOUBLE PRECISION is COMPLEX*16.  REAL*8 and COMPLEX*16
may be written in type statements, IMPLICIT, after a name (COMPLEX
Z*16) and before FUNCTION.  Other lengths, INTEGER*2 and LOGICAL*1,
are accepted and get a fullword.
From MIL-STD-1753 (1978): END DO, as a labelled DO's terminal
statement, and DO WHILE (e), labelled or not.  And, as VAX FORTRAN and
later Fortran 90 have it, a DO without a label ended by END DO, and a
labelled DO WHILE ended by any statement bearing the label.

Floating point, measured against the exact values (2026-10-15, TK5;
a unit is one in the last hexadecimal place of the result):

  Constants and READ: a decimal number in the source and the same
  number read by E, F, D, G or list-directed input are the same value,
  the nearest one of the format.  FORTRAN H truncates a REAL one, so a
  REAL constant here can be one unit above H's (0.1 is 4119999A, H's
  41199999), and so can whatever a program computes from it; H's
  DOUBLE PRECISION ones are up to 8 units off either way.

  Output: E, F, D and G editing print the value's own digits, rounded
  at the last one printed, to any width; a half rounds away from zero.
  H's DOUBLE PRECISION output can be a few units off in the 16th digit
  and pads with zeros past the 17th.

  Arithmetic is the machine's own, the same as H's to the bit.  So are
  SNGL, FLOAT, IFIX and the integer power X**I (repeated multiplication;
  X**39 can be 150 or 200 units off, in both).  A constant expression the
  compiler works out gives the bits the running program would.

  REAL functions are computed in long precision and cut to short:
  within a unit, and nearly always the exact value truncated, at any
  argument.  FORTLIB's short routines, which H's programs call, round
  SQRT and EXP and use their own approximations for the others, up to
  nine units off (SIN, ATAN2), and X**Y over 300.  The two agree bit
  for bit for some arguments only; a program that feeds such results
  back into itself (a network training, an integration) carries the
  difference along, and its printed REAL values can part from H's in
  the seventh significant digit: Xortran's loss after 20 epochs is
  0.197064698 here and 0.197064757 under H.  Where TANH is within a
  unit of 1, H returns 1.0.

  DOUBLE PRECISION functions: DSQRT is correctly rounded, as FORTLIB's
  is.  DEXP, DLOG, DLOG10, DATAN, DATAN2, DASIN, DACOS, DSINH, DCOSH,
  DTANH, DTAN and D**D are within 0.7 of a unit, and correctly rounded
  for all but about one argument in a hundred; FORTLIB's are within 1
  or 2 (DLOG10 6, DATAN2 5, D**D 400; DTAN off by thousands even at
  |x| < 20).  DSIN and DCOS are within 2 units for any argument;
  FORTLIB's are off by thousands at |x| < 20 as well.  FORTLIB's
  routines, hand-written assembler, take a fifth to a tenth of the
  time of these.

  COMPLEX functions (CSQRT, CEXP, CLOG, CSIN, CCOS, CABS) are within a
  unit of the result's magnitude; FORTLIB's, 14.  So is complex
  division, done in double precision, where FORTLIB's is within 12.

  SIN, COS and TAN reduce any argument exactly, by the bits of 2/pi;
  FORTLIB refuses a REAL argument of pi*2**18 or more and a DOUBLE
  PRECISION one of pi*2**50, and below that its DOUBLE PRECISION
  results have lost seven of their sixteen digits by 10**6.  MOD, AMOD
  and DMOD, though, are the textbook a-INT(a/b)*b, and when a/b is past
  an integer's range the result means nothing, in both.

Errors: fort370's runtime prints no messages for floating point.  An
overflow in arithmetic (1.0E70*1.0E70) abends with S0CC and a division
by zero with S0CF; FORTLIB intercepts those (IHC207I, IHC209I), carries
on with the largest number or zero, and ends the program after ten
such errors.  Underflow is zero, as in H.  A function's argument out of
its domain gets a value and no message, where FORTLIB prints an IHC
message for each and carries on:

  call              fort370        FORTRAN H
  SQRT(-4.0)        2.0            2.0
  ALOG(0.0)         -7.2E75        -7.2E75
  ALOG(-1.0)        -7.2E75        0.0
  EXP(200.0)        7.2E75         7.2E75
  ASIN(1.5)         1.5707963      0.0
  TAN(1.5707963)    3.2E6          7.2E75 (a singularity, it says)
  (-2.0)**0.5       0.0            1.4142135
  0.0**0.0, 0**0    1              0

IBM's names ARSIN, ARCOS, DARSIN and DARCOS are ASIN, ACOS, DASIN and
DACOS.


Rebuilding it yourself
----------------------

You need mvslovers' cc370 toolchain and libc370 installed, and then,
from a fort370 checkout:

    make mvs

which builds out/mvs/FORT370.xmit (the compiler, with cc370) and
out/mvs/F77RT.obj (the runtime and the libc370 members it calls,
bench/mkrtlib.py).  The assembler's and linker's clock is pinned
(MVSDATE, MVSTIME in the Makefile), since as370 and ld370 stamp the
date and time into what they write; two builds of the same source are
then the same bytes, and the SHA256 above reproduces.

  --sparse-text leaves the compiler's zeroed tables out of the module:
  program fetch hands over storage no text record covers as zeros.
  That is how MVS 3.8j behaves rather than something it promises; it
  is what cobc370 relies on too.

  -O1 because cc370's backend documents -O2 and above as unsafe on this
  target (the runtime was miscompiled at -O2: a double argument's store
  scheduled past the call).

bench/port-sweep.py is the proof that the compiler on MVS is the
compiler on the host: it compiles every FCVS program and every test on
the guest and diffs the assembler, byte for byte, with the host's.
